# Items — автоматизация мониторинга в Grafana

In-memory CRUD на Go: три REST-ручки, метрики latency, RPS и ошибок, дашборд Grafana, который собирается по живому списку ручек, и непрерывная фоновая нагрузка k6. Два экземпляра одного образа работают как два пода в разных датацентрах. Prometheus скрейпит оба.

## Запуск

Нужны Docker и Docker Compose. Go на хосте не нужен: приложение собирается внутри Compose. Версии образов зафиксированы в `.env.example`, тега `latest` нет.

```sh
cp .env.example .env
docker compose up
```

Пароль в `.env` заполнять не нужно. Сборка образов, генерация пароля Grafana, datasource, дашборд и нагрузка входят в эти две команды. Через 2–3 минуты на дашборде уже есть данные: разгон до полки занимает две минуты.

| Адрес | Что это |
|---|---|
| http://127.0.0.1:8081 | `app-1`, `POD_ID=1`, `DATACENTER=dc-1` |
| http://127.0.0.1:8082 | `app-2`, `POD_ID=2`, `DATACENTER=dc-2` |
| http://127.0.0.1:9090 | Prometheus, job `items-app`, scrape обоих приложений раз в 5 с |
| http://127.0.0.1:3000/d/items-service | Дашборд, UID `items-service` |

Порты опубликованы только на `127.0.0.1`. Оба приложения — образ `highload-lab1-app:local`. Внутри сети Compose они доступны как `app-1:8080` и `app-2:8080`.

Остановка:

```sh
docker compose stop    # контейнеры остановлены, volumes на месте
docker compose down    # контейнеры удалены, volumes на месте
docker compose down -v # вместе с базой Grafana, метриками и паролем
```

Записи приложений живут в памяти процесса и пропадают при перезапуске контейнера независимо от volumes.

## Пароль Grafana

В `.env.example` указаны `GRAFANA_ADMIN_USER=admin` и пустой `GRAFANA_ADMIN_PASSWORD=`. Файл `.env` в Git не входит.

Одноразовый `stack-init` при первом запуске записывает username и password в named volume `credentials` и завершается. Повторный запуск использует ту же пару. Свой пароль можно положить в `.env` до первого старта. Если заданная пара не совпадает с уже сохранённой, init останавливается и не меняет пароль молча. Смена `.env` не меняет пароль уже созданной базы Grafana.

Grafana и генератор дашборда читают volume и получают учётные данные через окружение. Пароль в лог не пишется. Чтобы войти в UI:

```sh
docker run --rm -v highload-lab1_credentials:/credentials:ro alpine:3.24.3 cat /credentials/username /credentials/password
```

Команда для входа в интерфейс, для запуска стека она не нужна. Вывод — секрет: его не показывают в скринкасте, PR и общих логах. Datasource и дашборд к этому моменту уже созданы, настраивать их вручную не нужно.

## Порядок старта

| Сервис | Когда стартует |
|---|---|
| `stack-init` | Сразу, пишет credentials и завершается |
| `app-1`, `app-2`, Prometheus | Параллельно с init |
| Grafana | После успешного init. Datasource Prometheus с UID `prometheus` приходит из provisioning |
| `dashboard-generator` | После healthy приложений, Prometheus и Grafana. Читает `GET /handlers` и записывает дашборд |
| k6 | После healthy приложений и успешного завершения генератора |

Генератор и k6 не перезапускаются. Если генератор завершился с ошибкой, нагрузка не стартует.

## API

Ровно три бизнес-ручки. ID назначает сервис, это UUID. Тело `POST` и `PUT` — JSON `{"name":"...","value":"..."}`. Оба поля обязательны и непустые.

| Метод и путь | Успех | Ошибка |
|---|---|---|
| `POST /items` | `201`, созданная запись | `400` на некорректное тело |
| `GET /items/{id}` | `200`, запись | `404`, если записи нет |
| `PUT /items/{id}` | `200`, обновлённая запись | `404`, если записи нет; `400` на некорректное тело |
| `GET /health` | `200`, `{"status":"ok"}` | — |
| `GET /metrics` | текст Prometheus | — |
| `GET /handlers` | каталог бизнес-ручек | — |

```sh
curl -sS -D - -X POST http://127.0.0.1:8081/items \
  -H 'Content-Type: application/json' \
  -d '{"name":"n","value":"v"}'
```

Хранилище — `sync.Map` внутри процесса. У подов независимые данные: ID, созданный на `8081`, на `8082` не существует. TTL и `DELETE` нет, поэтому успешные `POST` увеличивают память процесса.

`GET /handlers` возвращает только бизнес-ручки:

```json
{
  "handlers": [
    {"method": "POST", "path": "/items"},
    {"method": "GET", "path": "/items/{id}"},
    {"method": "PUT", "path": "/items/{id}"}
  ]
}
```

## Метрики

Сбор — в `pkg/monitoring`, отдельный Prometheus registry. Служебные `/health` и `/metrics` в метрики не входят. `/handlers` тем же middleware учитывается, но в каталог и на дашборд не попадает.

| Метрика | Тип | Лейблы |
|---|---|---|
| `http_requests_total` | Counter | `pod_id`, `datacenter`, `method`, `route`, `status_code` |
| `http_request_duration_seconds` | Histogram | `pod_id`, `datacenter`, `method`, `route` |

`pod_id` и `datacenter` берутся из `POD_ID` и `DATACENTER` и не меняются за жизнь процесса. `method` и `route` берутся из регистрации ручки: шаблон `/items/{id}`, а не фактический путь и не UUID. Иначе каждый ID дал бы отдельный ряд. Код ответа есть только у счётчика. Отдельной метрики ошибок нет: панель ошибок — срез того же счётчика по `status_code=~"4..|5.."`.

### Почему Histogram

Нужны перцентили по нескольким экземплярам сразу. Summary считает квантиль внутри процесса и отдаёт готовое число. Среднее двух p95 не равно p95 объединённых запросов: квантиль — позиция в распределении, а распределение при отдаче готового числа уже потеряно.

Histogram отдаёт кумулятивные счётчики `_bucket` с общей границей `le`. Счётчики складываются. Сначала `sum by (le)` по выбранным подам и датацентрам, затем `histogram_quantile`. Оценка общая для выбранного набора экземпляров. Точность ограничена шириной бакета: значение интерполируется внутри интервала.

Границы одинаковые у всех экземпляров и не читаются из окружения. Клиент Prometheus сам добавляет `+Inf`. Конечные границы в секундах:

```text
0.0000005, 0.000001, 0.0000025, 0.000005,
0.00001, 0.000025, 0.00005, 0.0001, 0.00025, 0.0005,
0.001, 0.0025, 0.005, 0.01, 0.025, 0.05,
0.1, 0.25, 0.5, 1, 2.5, 5
```

Нижняя граница `500ns`: метрика измеряет время обработчика в процессе, без сети. У in-memory ручек это микросекунды. При первой границе `100µs` почти все наблюдения попадали в один бакет, и перцентили переставали различаться.

Пример для `POST /items`. Для `GET` и `PUT` меняются `method` и `route`.

```promql
histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket{job="items-app",method="POST",route="/items",datacenter=~`${datacenter:regex}`,pod_id=~`${pod_id:regex}`}[$__rate_interval])))

sum(rate(http_requests_total{job="items-app",method="POST",route="/items",datacenter=~`${datacenter:regex}`,pod_id=~`${pod_id:regex}`}[$__rate_interval]))

sum by (status_code) (rate(http_requests_total{job="items-app",method="POST",route="/items",datacenter=~`${datacenter:regex}`,pod_id=~`${pod_id:regex}`,status_code=~"4..|5.."}[$__rate_interval]))
```

Селекторы `datacenter` и `pod_id` записаны raw-строкой PromQL. Grafana экранирует точку в значении одним слэшем, и Prometheus 3 принимает такой regex. Для `dc-1` и `1` экранирование ничего не меняет.

RPS — сумма скоростей выбранных экземпляров, не среднее. Перцентили считаются по сумме бакетов, а не усредняются между подами. `rate` берётся до суммирования, чтобы перезапуск пода не ломал расчёт.

## Дашборд

Генератор (`cmd/dashboard-generator`) не содержит списка ручек. Он читает `GET /handlers` и на каждую пару метод/путь создаёт три панели: latency (p50, p95, p99), RPS и ошибки по коду. Для трёх ручек это девять панелей. Повторный запуск обновляет дашборд с тем же UID и не создаёт копию. Ручка, исчезнувшая из каталога, с дашборда уходит.

Переменные `datacenter` и `pod_id` — multi-select и All. All выбрано с самого начала, даже если рядов ещё нет. Списки обновляются при загрузке дашборда и при смене временного диапазона.

Дашборд записан с `editable: false`. У администратора Grafana права на изменение остаются: это свойство дашборда, а не ограничение роли. Модель собирается Grafana Foundation SDK и пишется в Dashboard API Grafana `13.3.0`.

Новая ручка появляется без правок генератора. Её регистрируют в приложении тем же механизмом и пересобирают стек:

```sh
docker compose up --build
```

## Нагрузка

Один процесс `grafana/k6:1.6.0`. Executor `externally-controlled` с `duration: "0s"` в этой версии работает, пока процесс не остановят. В k6 2.x этого executor нет, поэтому образ не обновляется на ветку 2.x. Это paced closed workload: 30 VU не означают 30 RPS. Занятый слот пропускается и пачкой потом не выполняется.

Суммарно на оба экземпляра, `t` — секунды от старта:

```text
R(t) = 5 + 25 * min(t / 120, 1)
```

За 120 секунд цель растёт с 5 до 30 RPS и остаётся на 30 RPS, пока стек не остановят. `docker compose down` и сигнал процессу останавливают k6, автоматического перезапуска нет.

Поды чередуются. На цикле из 200 слотов: 91 `GET`, 91 `PUT`, 10 успешных `POST`, 4 `GET` несуществующего ID (`404`), 2 `POST` и 2 `PUT` с битым телом (`400`). Это около 2% ответов `404` и около 2% ответов `400`. Расписание ошибок не привязано к одному поду. Постоянных `500` нагрузка не создаёт: сбор и панель этого кода проверяются отдельно.

`setup()` один раз создаёт по записи на каждом поде. Дальше успешные `POST` продолжаются, примерно 5% слотов. Скрытого лимита и TTL нет, поэтому память приложений растёт вместе с числом записей.

## Состав

| Каталог | Что там |
|---|---|
| `cmd/app` | HTTP-сервер |
| `cmd/dashboard-generator` | Чтение `/handlers` и запись дашборда |
| `cmd/stack-init` | Одноразовая запись credentials |
| `internal/httpapi` | REST на стандартном `http.ServeMux` |
| `internal/item` | Запись и `sync.Map` |
| `internal/dashboard` | JSON дашборда и клиент Grafana |
| `pkg/monitoring` | HTTP-метрики и каталог ручек |
| `deploy/prometheus` | Scrape двух экземпляров |
| `deploy/grafana/provisioning` | Datasource Prometheus |
| `load` | Сценарий k6 |

Точки входа собирают зависимости через конструкторы. Хранилище не знает про HTTP и метрики. Генератор не импортирует обработчики и получает каталог только по HTTP.
