# Highload Lab 1 — автоматизация мониторинга Grafana

Учебный проект по [TASK.md](TASK.md). Подробный порядок реализации и приемки — в [plan/README.md](plan/README.md).

## Текущее состояние

Базовый HTTP-сервис принимает `POST /items`, `GET /items/{id}`, `PUT /items/{id}` и служебные `GET /health`, `GET /metrics`, `GET /handlers`. Записи хранятся в памяти процесса и не удаляются. `docker compose up` собирает локальные образы, генерирует пароль Grafana и запускает два экземпляра, Prometheus и Grafana. Генератор дашборда и сценарий k6 еще не реализованы: `dashboard-generator` завершается с кодом `1`, поэтому k6 не стартует.

## Запуск стенда

Из корня проекта:

```sh
cp .env.example .env
docker compose up
```

Пустой `GRAFANA_ADMIN_PASSWORD` — это не пароль и не запасной `admin`. `stack-init` один раз генерирует пароль через `crypto/rand` и сохраняет пару в named volume `credentials`. Повторный запуск использует ту же пару. Другое непустое значение в `.env` не заменяет уже сохраненный пароль: initializer завершается с ошибкой и не печатает секрет. `docker compose down -v` удаляет credentials вместе с данными Grafana.

На хосте опубликованы только loopback-порты: приложение `http://127.0.0.1:8081` и `http://127.0.0.1:8082`, Prometheus `http://127.0.0.1:9090`, Grafana `http://127.0.0.1:3000`. Между контейнерами адреса другие: `app-1:8080`, `app-2:8080`, `http://prometheus:9090`. Оба приложения запускаются из образа `highload-lab1-app:local` с `POD_ID=1`/`DATACENTER=dc-1` и `POD_ID=2`/`DATACENTER=dc-2`.

Пароль не хранится в репозитории. Локально его можно прочитать из volume; вывод содержит секрет, его не нужно переносить в скринкаст, PR или общие логи:

```sh
docker run --rm -v highload-lab1_credentials:/credentials:ro alpine:3.24.3 cat /credentials/username /credentials/password
```

## Локальный запуск API

Из корня проекта:

```sh
POD_ID=local DATACENTER=local go run ./cmd/app
```

По умолчанию процесс слушает `:8080`. Настройки HTTP читаются из `config.yaml` в рабочей директории; переменные окружения перекрывают файл. Если значения нет ни в файле, ни в окружении, остается значение по умолчанию. Другой файл задается через `CONFIG_PATH`. `POD_ID` и `DATACENTER` задаются только окружением и проверяются до открытия порта: пустое или неподходящее значение завершает процесс с ошибкой. Файл конфигурации их не задает.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `HTTP_ADDR` | `:8080` | Адрес `host:port` |
| `HTTP_READ_HEADER_TIMEOUT` | `2s` | Таймаут чтения заголовков |
| `HTTP_READ_TIMEOUT` | `5s` | Таймаут чтения запроса |
| `HTTP_WRITE_TIMEOUT` | `10s` | Таймаут записи ответа |
| `HTTP_IDLE_TIMEOUT` | `60s` | Таймаут keep-alive |
| `HTTP_SHUTDOWN_TIMEOUT` | `15s` | Ожидание активных запросов после SIGINT/SIGTERM |
| `HTTP_MAX_BODY_BYTES` | `65536` | Предельный размер тела, верхняя граница `1048576` |
| `POD_ID` | нет | Идентификатор пода, лейбл `pod_id` |
| `DATACENTER` | нет | Идентификатор датацентра, лейбл `datacenter` |

`POD_ID` и `DATACENTER` — это 1–63 символа: буква или цифра в начале и в конце, внутри также допустимы `.`, `_` и `-`. Например, `app-1` и `dc-a`. Пробел, путь и перевод строки не подходят. Границы histogram из окружения не читаются.

`POST` и `PUT` принимают JSON `{"name":"...","value":"..."}` с `Content-Type: application/json`. Оба поля обязательны и не могут быть пустыми. ID создает сервис; поле `id` в теле — некорректный запрос. `PUT` заменяет `name` и `value` существующей записи и сохраняет ID из пути. Успешные ответы содержат `id`, `name` и `value`. Ошибки имеют вид `{"error":"..."}`: `400` для некорректного ввода, `404` для неизвестного ID, `500` для внутренней ошибки без текста причины. Пока процесс готов, `GET /health` возвращает `200` и `{"status":"ok"}`; с началом остановки готовность снимается. Отдельной команды или режима запуска для проверки нет.

## Метрики

Библиотека `pkg/monitoring` получает уже проверенные `POD_ID` и `DATACENTER` через конструктор и пишет их в отдельный Prometheus registry. Глобальный registry и стандартные process/Go collectors не используются. Наблюдения появляются только от реальных запросов к инструментированным ручкам: при старте процесс не делает искусственных вызовов, чтобы «проявить» ряды.

| Метрика | Тип | Лейблы |
|---|---|---|
| `http_requests_total` | Counter | `pod_id`, `datacenter`, `method`, `route`, `status_code` |
| `http_request_duration_seconds` | Histogram | `pod_id`, `datacenter`, `method`, `route` |

`route` — шаблон, переданный при регистрации, например `/items/{id}`. Фактический путь, id записи, query string, полный URL и текст ошибки в лейблы не попадают. `method` тоже берется из регистрации, а не вычисляется заново из произвольной строки запроса. `pod_id` и `datacenter` постоянны для процесса.

Отдельного счетчика ошибок нет. RPS — это `sum(rate(http_requests_total[window]))` по выбранным подам и датацентрам. Ошибки — тот же счетчик, отфильтрованный по `status_code` для `4xx` и `5xx`, с сохранением конкретного кода. `rate` дает ошибки в секунду, `increase` — оценку числа за окно. Код ответа есть только у счетчика: latency успешных и ошибочных ответов лежит в одном histogram, и перцентили можно складывать по бакетам.

Latency — классический Histogram, не Summary. Summary отдает уже посчитанные квантили, и их нельзя корректно усреднить между подами. Histogram экспортирует `_bucket`, `_sum` и `_count`. Общий перцентиль считается по сумме бакетов:

```promql
histogram_quantile(q, sum by (le) (rate(http_request_duration_seconds_bucket[window])))
```

`histogram_quantile` линейно интерполирует внутри интервала `(предыдущая граница, граница]`, в который попал ранг. Нижняя граница первого интервала — 0. Если ранг оказывается в `+Inf`, оценка ограничена последней конечной границей, хвост выше нее не разрешается. Чем шире бакет, тем грубее перцентиль. Одинаковые границы на всех экземплярах позволяют суммировать `rate` по `le`; они не делают оценку точнее ширины бакета и не настраиваются переменными окружения. `+Inf` добавляет клиент Prometheus, в коде его нет.

Конечные границы в секундах: `0.0000005, 0.000001, 0.0000025, 0.000005, 0.00001, 0.000025, 0.00005, 0.0001, 0.00025, 0.0005, 0.001, 0.0025, 0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5`.

Нижняя граница `500ns`, а не `100µs`: histogram измеряет время внутри обертки обработчика, без сети. На darwin/arm64 и Go 1.26.0 локальный прогон 200 горячих итераций дал среднее около `1.3µs` у `GET`, `3.4µs` у `PUT` и `5.5µs` у `POST`; при первой границе `100µs` почти все наблюдения схлопывались в один бакет. После уточнения общего набора масса `GET` лежит в `(0.5µs, 5µs]`, `PUT` и `POST` — в основном в `(1µs, 10µs]`, ниже `500ns` попаданий не было. Это замер времени обработчика в процессе, не RTT клиента и не гарантия под нагрузкой.

Служебные ручки:

- `GET /metrics` отдает registry в текстовом формате Prometheus и не входит в HTTP-метрики.
- `GET /health` тоже не входит в HTTP-метрики.
- `GET /handlers` инструментируется тем же middleware, но не входит в бизнес-каталог. Будущий дашборд строится по каталогу, поэтому собственный RPS `/handlers` не смешивается с RPS бизнес-ручек.

Пример каталога:

```json
{
  "handlers": [
    {"method": "POST", "path": "/items"},
    {"method": "GET", "path": "/items/{id}"},
    {"method": "PUT", "path": "/items/{id}"}
  ]
}
```

Регистрация одновременно кладет обработчик в `http.ServeMux`, при необходимости оборачивает его метриками и отдельно решает, попадает ли шаблон в каталог. Список бизнес-ручек не дублируется вручную. Счетчик увеличивается один раз на запрос и хранит первый окончательный HTTP-код, включая неявный `200`. Повторный `WriteHeader` и ответ `500` после panic не подменяют статус, если ответ уже начат. Восстановление после panic находится внутри этой обертки, чтобы в метрику попал итоговый код; для клиента по-прежнему отдается JSON `{"error":"internal error"}` без текста panic.

## Структура и зависимости компонентов

| Каталог | Ответственность |
|---|---|
| `cmd/app` | Сборка зависимостей и запуск HTTP-сервера |
| `cmd/dashboard-generator` | CLI обнаружения ручек и генерации дашборда |
| `cmd/stack-init` | Одноразовая инициализация локальных credentials |
| `internal/config` | Загрузка `config.yaml` и переменных окружения через cleanenv |
| `internal/item` | Модель записи и хранилище на `sync.Map` |
| `internal/httpapi` | REST-обработчики и стандартный `http.ServeMux` |
| `internal/dashboard` | JSON дашборда и клиент Grafana API |
| `pkg/monitoring` | Переиспользуемая библиотека HTTP-метрик и обнаружения ручек |
| `deploy/scripts` | Будущий entrypoint загрузки credentials в environment |
| `deploy/prometheus` | Будущая конфигурация scrape |
| `deploy/grafana/provisioning/datasources` | Будущий provisioning datasource |
| `load` | Будущий сценарий k6 |

Каталоги будущих конфигураций сохранены через `.gitkeep`, а пустые Go-пакеты — через файл с объявлением `package`. Полный набор каталогов из стороннего шаблона standard layout не копируется: используются только нужные проекту `cmd`, `internal`, `pkg` и `deploy`.

Точки входа в `cmd` — composition roots. Конфигурация, хранилище, registry метрик и HTTP-обработчики передаются через конструкторы, без DI-фреймворка и package-level singleton. Клиент Grafana будет передан так же. Хранилище не зависит от HTTP или метрик. Генератор не импортирует бизнес-обработчики и получает каталог только по HTTP в runtime.

`monitoring.NewRegistry()` создает отдельный Prometheus registry. HTTP-метрики, каталог `/handlers` и проверка `POD_ID`/`DATACENTER` регистрируются в нем явно, без глобального состояния.

Имя модуля — `highload/lab1`: публичный URL репозитория еще не задан. Это рабочий локальный module path, а не выдуманный GitHub-адрес. При публикации его можно заменить на фактический module path вместе с внутренними импортами.

### Контракты совместимости

- Go client экспортирует классический Prometheus Histogram и Counter в текстовом формате Prometheus. Выбранный Prometheus поддерживает `rate`, `sum`, `histogram_quantile` и HTTP API `/api/v1/query` для этих рядов.
- Для Grafana выбран документированный Dashboard API `dashboard.grafana.app/v1`: `POST /apis/dashboard.grafana.app/v1/namespaces/default/dashboards` для создания и `GET`/`PUT` по тому же пути с UID для чтения/обновления. JSON модели дашборда помещается в `spec`; фиксированный UID задается через `metadata.name`. SDK не используется. Сохраняются admin HTTP Basic-аутентификация, фиксированный datasource UID и `editable: false`. Детали версии/конфликтов проверяются при реализации клиента.
- k6 намеренно не обновлен до текущей ветки 2.x: план опирается на `externally-controlled` с `duration: "0s"` в версии 1.6.0. Один процесс с JS pacing должен разгоняться до суммарных 30 RPS за две минуты и работать до остановки, без повторного ramp-up. VU не равны RPS; фактическая скорость проверяется мониторингом.

Это выбор совместимых документированных контрактов. Scrape двух экземпляров и provisioning datasource проверены. Импорт JSON дашборда, admin-клиент генератора и непрерывность k6 остаются этапам 5–7.

Из корня проекта:

```sh
go test -mod=readonly ./...
go test -mod=readonly -race ./...
go vet -mod=readonly ./...
go build -mod=readonly -o bin/ ./cmd/...
go mod verify
```

Эти команды проверяют хранилище, контракт трех бизнес-ручек, готовность, остановку сервера, изоляцию registry, лейблы, histogram, каталог `/handlers` и bootstrap credentials. Генератор дашборда и сценарий k6 из шагов 5–6 пока не реализованы.

Go может автоматически загрузить рекомендованный toolchain. Для проверки установленным Go ветки 1.26 допустимо явно задать `GOTOOLCHAIN=local`, но такой прогон нужно отличать от проверки именно на 1.26.8.

## Dockerfile каркаса

Сборка трех отдельных runtime-образов:

```sh
docker build --target app -t highload-lab1-app:dev .
docker build --target dashboard-generator -t highload-lab1-dashboard-generator:dev .
docker build --target stack-init -t highload-lab1-stack-init:dev .
```

Без `--target` собирается app. Приложение и генератор работают от `10001:10001`. `stack-init` работает от root, потому что создает приватный volume и выставляет общую группу `10000`: каталог `0750`, файлы `0640`, без чтения для остальных. Grafana и генератор монтируют volume только на чтение и входят в эту группу. Секреты не передаются через build args. Генератор по-прежнему завершается с кодом `1`, пока не выполнен шаг 5. Обычный запуск — `docker compose up`: он сам собирает отсутствующие локальные образы.

## Архитектурные ограничения следующих этапов

- Ровно три бизнес-ручки: `POST /items`, `GET /items/{id}`, `PUT /items/{id}`. Для отсутствующего ID — `404`. `GET /metrics` и `GET /handlers` служебные и не увеличивают бизнес-каталог. `/health` сообщает о готовности и в метрики не входит.
- `/handlers` инструментируется и возвращает только бизнес-каталог для будущего генератора.
- Latency — Histogram с едиными фиксированными бакетами на всех экземплярах; RPS и ошибки — Counter с HTTP-кодом. Перцентили считаются по сумме rate бакетов, а не усредняются между подами.
- Два приложения используют один образ, но разные runtime `POD_ID` и `DATACENTER`. Хранилища независимы, не реплицируются и теряются при перезапуске.
- Host-порты Compose: app — `127.0.0.1:8081` и `127.0.0.1:8082`, Prometheus — `127.0.0.1:9090`, Grafana — `127.0.0.1:3000`. Локальный процесс слушает `HTTP_ADDR` (по умолчанию `:8080`).
- В `.env.example` нет действующего пароля: пустой `GRAFANA_ADMIN_PASSWORD` запускает генерацию через `crypto/rand`. `stack-init` сохраняет пару в приватном named volume, entrypoint читает файлы как данные и экспортирует credentials в env перед `exec`. Повторный запуск переиспользует ту же пару; молчаливая ротация недопустима.
- Порядок старта: успешный init, затем healthy приложения и Grafana, затем генератор, затем k6. Пока генератор завершается с ошибкой, k6 не запускается.
- `.env`, локальные секреты, кэши и артефакты исключены из Git и Docker build context. Файл `.env.example` — пример, не хранилище секрета.
